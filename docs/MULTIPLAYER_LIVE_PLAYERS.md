# Живые игроки в матчах: логика и архитектура

## Цель

- Два **реальных** игрока могут сыграть друг с другом.
- Правило продукта: **один живой игрок в «экосистеме матча» = минус один бот** (боты — заполнители, когда живых мало).

Сейчас в коде все соперники — локальные боты (`bot-*`), матчмейкинг имитируется таймером. Ниже — как это изменить **логически**, без привязки к конкретному вендору WebSocket.

---

## 1. Что считать «живым» игроком

- Авторизован через ВК, есть стабильный `userId` (`vk_*`).
- Подключён к **сессии матчмейкинга** (очередь) или к **активному матчу** (комната).

Гость (`guest_*`) может не попадать в PvP с живыми или попадать только в отдельную очередь — на усмотрение продукта.

---

## 2. Принцип «один живой — минус один бот»

### Смысл

- Боты в UI (список ставок, «подбор соперника») — **не бесконечная реальность**, а **ёмкость лобби**.
- Обозначим:
  - `B` — целевое число **слотов под ботов** (например, как сейчас в списке ставок).
  - `L` — число **живых игроков**, которые сейчас в очереди на матч **или** уже в паре (считаются по-разному — см. ниже).

**Вариант A (простой):**  
`botsVisible = max(0, B - L_queue)`  
где `L_queue` — живые **в очереди** (ещё без пары). Пока люди ждут пару, «фейковых» ботов показываем меньше.

**Вариант B (строже к формулировке):**  
Каждый живой, **уже сопоставленный** в матч, убирает из пула **одного** бота-заполнителя на время матча:  
`botsActive = B - pairedHumans`  
(пары считаются как `pairedHumans = floor(playersInMatches / 2)` в рамках одного режима/ставки, если делите пул по корзинам).

**Рекомендация:** комбинировать — уменьшать видимых/генерируемых ботов и при **очереди**, и при **активных PvP-матчах**, чтобы не «раздувать» ощущение фейка при онлайне.

---

## 3. Матчмейкинг (сервер — источник правды)

### Корзина матча

Игроки должны попадать в одну корзину, иначе честного матча нет:

| Параметр | Зачем |
|----------|--------|
| `bet` (или диапазон) | Одинаковая экономика |
| `totalRounds` (1 / 3 / 5) | Одинаковый формат |
| `weeklyMode` (если важно) | Одинаковые правила ивента |
| `clientVersion` (опционально) | Совместимость правил |

### Алгоритм

1. `POST /api/match/queue` — игрок входит в очередь с параметрами корзины.
2. Сервер ищет **другого** игрока в **той же** корзине (FIFO или по рейтингу — позже).
3. Если нашёлся — создаётся `matchId`, обоим отдаётся **профиль соперника** (id, имя, аватар — из БД / VK).
4. Если за `T` секунд пары нет — **откат к боту** (текущее поведение) *или* продолжение ожидания — политика продукта.

### «Минус один бот»

- Пока игрок **в очереди**, уменьшить число **генерируемых** ботов-строк в списке ставок / сайдбара (см. §2).
- После создания пары **два** живых заняли один матч — из пула на это время вычитается **два** «эквивалента бота» (или один «полный матч»), чтобы не перегружать лобби фейком.

## 4. Игровой раунд (нельзя оставить только на клиенте)

При двух живых **нельзя** доверять клиенту исход раунда (читерство).

Минимально честная схема:

1. Оба отправляют на сервер **ход** + `matchId` + `round` + **дедлайн** по времени.
2. Сервер ждёт оба хода или таймаут (проигрыш по таймауту — как в одиночной игре).
3. Сервер считает победителя раунда и обновляет счёт; отдаёт обоим **одинаковый** `roundResult`.
4. Режим «Слепая удача»: сервер **не отдаёт** ставку/ход соперника до момента, зафиксированного правилами (например, до `locked` для обоих).

Канал доставки: **WebSocket** (предпочтительно) или long-polling для MVP.

## 5. Изменения в клиенте (высокоуровнево)

| Место | Сейчас | Нужно |
|-------|--------|--------|
| Переход в матчмейкинг | ~~`pickRandomOpponent()` сразу~~ | **Сделано (MVP):** `vk_*` → `POST /api/match/queue` + `GET /api/match/poll`; гость — бот без очереди; таймаут → `ensureRandomBotOpponent()` |
| Арена | Ход бота генерируется локально | Если `opponent.id` — живой `vk_*`, ходы приходят с сервера / отправляются на сервер |
| Список ставок / боты | Фиксированные боты | `effectiveBotCount = f(B, liveQueue, activeMatches)` |

---

## 6. Данные на сервере (черновик)

- `MatchQueueEntry`: `userId`, `bet`, `rounds`, `mode`, `enqueuedAt`
- `Match`: `id`, `playerA`, `playerB`, `state`, `currentRound`, `scores`, `expiresAt`
- `MatchRound`: хранение ходов для аудита (опционально)

Хранилище: уже есть JSON `players.json`; для очередей и матчей лучше **Redis** или отдельные таблицы/файлы с блокировками, чтобы два запроса не создали один матч дважды.

---

## 7. Этапы внедрения

1. **Очередь + пара по HTTP** (polling): без WS, только «найти пару», затем оба заходят в матч по `matchId` (хуже по UX, проще отладка).  
   **Реализация в коде:** `lib/match-queue-store.ts` (состояние очереди в SQLite `game-state.sqlite` через `lib/server-game-db.ts`, чтобы PM2 cluster / несколько воркеров видели одну очередь), `app/api/match/queue/route.ts` (POST/DELETE), `app/api/match/poll/route.ts` (GET), клиент — `components/matchmaking.tsx`. Корзина: `bet` + `totalRounds` + `weeklyMode`. Heartbeat «онлайн» — таблица `presence` в том же SQLite (`lib/presence-store.ts`).
2. **WebSocket**: push «соперник найден», «соперник сходил», «раунд завершён».
3. Подкрутить **формулу ботов** в UI под §2.
4. Анти-чит: только сервер считает исход; клиент только отображает.

---

## 8. Риски

- **Нагрузка** на сервер при росте онлайна — нужен масштабируемый слой очередей.
- **AFK** — таймауты и штрафы (проигрыш матча / рейтинг).
- **Синхронизация времени** — серверное время для дедлайнов хода (как уже сделано для LiveOps).
